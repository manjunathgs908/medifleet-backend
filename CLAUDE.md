# medifleet-backend — Claude Code Project Context

## What this repo is
Node.js / Express API for SaveLife Health Services (Bengaluru ambulance + medical
transport). Hosted on **Render**, auto-deploys from GitHub `main`.

- Live: `https://api.savelife.health`
- Database: **MongoDB Atlas**, database name `medifleet` (replica set)

This backend is the **single source of truth** for every client:
- `savelife-app` — customer React Native app
- `medifleet-app` — Expo driver app
- `savelife-web` — Next.js site (Vercel)
- CRM dispatch console — `crm.savelife.health`

A change here affects all four. Treat it that way.

---

## Hard rules — never break these

1. **NO HARDCODED PRICES, ANYWHERE.** Every fare, slab, wait-charge rate, add-on
   price, and cancellation charge is read from the `Pricing` collection at request
   time. If you find a rate literal in code, flag it — do not add another.
2. **Server time only.** `new Date()` on the server is the only acceptable source
   for trip timestamps, wait-clock start/stop, and anything billable. Never trust
   a client-supplied timestamp. Store the device-reported time separately if
   needed for drift analysis, but never bill from it.
3. **Money in integers.** Store paise, not floating-point rupees.
4. **Trip events are append-only.** Never update or delete a trip event.
   Corrections are new compensating events.
5. **Never break an existing API contract** without telling me. Four clients depend
   on these responses. Add fields; don't rename or remove them.
6. **Auth on every route.** No new endpoint ships without the correct auth
   middleware and role check.
7. **No new dependencies** without asking me first.

## Architecture notes

- Pricing is **slab-based** and **vehicle-type-specific**, stored in MongoDB.
- Trip lifecycle: 9 stages from START_TRIP through END_TRIP_CLOSE_DUTY,
  each capturing GPS + timestamp.
- Driver auth: Employee ID + PIN, with **device binding** (one driver, one device,
  one ambulance).
- Pickup OTP: 4-digit, auto-generated by a pre-save hook on the Trip model.
- `driverConfirmed` flag gates the customer-facing "Ambulance En Route" state.
- Cancellation: 9 reasons; ₹500 charge only after 5+ minutes.
- Google Places/Directions are **proxied through this backend** so keys stay
  server-side: `/api/places/autocomplete`, `/api/places/details`,
  `/api/places/reverse`, `/api/places/directions` (returns `overview_polyline`).

## Wait-charge structure (business-decided — these values live in MongoDB)

| Type | Free time | Rate after |
|---|---|---|
| Pickup wait | 10 min | ₹5/min |
| Traffic wait | none | ₹3/min |
| Drop wait — one-way | 10 min | ₹10/min |
| Drop wait — return trip | 10 min | ₹5/min for next 120 min, then ₹10/min |

**Traffic wait will not be implemented — this is a product decision, not a missing
feature.** It's too hard to explain to a customer mid-trip ("you were charged
because of traffic") and creates billing disputes. `trafficWaitPerMin` stays in
the `Pricing` schema and the table above for reference, but nothing reads it —
no code opens a traffic wait segment or bills against it. Don't build this
without an explicit reversal of the decision.

Rules:
- All wait time computed **server-side from the event log**. Clients display only.
- Cap total wait charges at **150% of base fare**.
- Each wait segment is a discrete record: start, end, rate, tier, amount.
- Drivers cannot edit timestamps. Ops adjustments require a reason + audit entry.

## Currently in progress
**Wait-charge feature.** Backend done: pickup wait (`PUT /api/trips/:id/arrive-pickup`)
and drop wait (`PUT /api/trips/:id/reached-hospital`, `PUT /api/trips/:id/start-return`)
both open/close wait segments, rates come from Pricing, live state is on the
trip read endpoints (`waitState`), and completeTrip bills pickup + drop
together. GPS guard is log-only (`ENFORCE_PICKUP_GPS_GUARD = false`) until the
driver app has an override UI.

**Driver app MUST ship "Reached Hospital" and "Starting Return" in the SAME
release.** Round-trip drop wait is bracketed `reachedHospitalAt -> returnStartedAt`.
If the app calls "Reached Hospital" but never calls "Starting Return" (i.e.
ships the first tap without the second), every round trip hits the
no-returnStartedAt fallback: drop wait is charged Rs 0 and the trip is flagged
`dropWaitNeedsReview` for manual billing. Not a silent bug, but it does mean
zero drop-wait revenue on every round trip until both taps exist client-side.
